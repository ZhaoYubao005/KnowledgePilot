KnowledgePilot 工程验证

Test 与 Evaluation
Test 验证程序是否按照设计工作。单元测试检查输入输出、参数解析、异常和接口结构，Mock 可固定工具结果与模型消息。测试通过说明被断言的行为符合预期，却不能证明知识库检索到了正确资料，也不能保证真实 Agent 总会选择合适工具。Evaluation 衡量 RAG 与 Agent 的实际表现，关注相关资料是否命中、必要工具是否使用、任务是否完成以及步骤和时间。两者可以使用相同函数，但检验的对象不同。程序正确地执行一次 search，仍可能把语义相似但不回答问题的片段排在前面；程序正确地执行 Agent Loop，也可能产生事实不足的答案。确定性的 Test 适合定位实现回归，真实服务的 Evaluation 适合观察整体质量。Mock 验证与真实评测需要分别记录，不能把模拟返回的好结果当成真实模型的能力。

Baseline 与固定材料
Baseline 是当前系统在固定 Evaluation Dataset 上、采用明确配置得到的基准成绩。Evaluation Dataset 固定有助于让不同版本面对相同任务；Corpus 固定有助于让不同检索方案搜索相同资料。即使查询文字不变，增删文档、改变正文、重新分块或更换向量模型，都可能改变检索排名。只固定问题而不断改变 knowledge base，难以判断变化来自算法还是语料。document_id 标识文档，chunk_index 标识文档内部片段，二者应绑定相同语料版本。当前分块使用五百字符和一百字符重叠，改动这些参数也会改变片段边界。Baseline 应记录检索范围、Top-K、是否应用阈值及使用的服务模型。它是特定条件下的比较参照，不是对所有未来问题的保证。新旧版本的对照应先保持任务、资料和计分口径一致，再讨论优化收益。比较应可复现。

Regression、Badcase 与 Ablation
Regression 指新版本使原本正常的能力退化。一次改动可能提高整体命中率，却让少量原本能检索到的关键片段消失，因此平均成绩与具体退化样本都值得检查。Badcase 是具体失败样本及原因分析，可以区分资料缺失、检索漏召回、相关片段排名靠后、工具选择不当、参数错误或服务异常。语义接近的片段未必回答同一件事，失败分析应回到实际正文与概念边界。Ablation 在其他条件固定时移除或禁用某个组件，分析其贡献。比较启用和关闭阈值过滤，保持 Corpus、问题集合和向量模型一致。比较两种 Top-K 属于参数对照，需要与组件消融区分。若同时改变分块、模型和查询表达，难以把提升归因于其中一个因素。一次较好的运行不足以解释原因，稳定对照与失败记录能为后续 Retrieval Optimization 提供依据。失败应分别记录，便于复查。

Latency 与已知技术债
Latency 表示完成一次明确操作所需的时间。检索耗时可以包含 Query Embedding 和 Vector Search，完整 Agent 耗时还可能包含多轮 Decision、工具执行与最终回答。不同计时范围的数值不能直接混用，首次模型加载和重复调用也应区分。KnowledgePilot 当前依赖外部运行的本地 Ollama 服务；服务是否可用、模型加载状态和机器负载可能影响耗时，模型或运行参数变化也可能影响回答与工具选择。当前文档 update 存在非原子技术债：先删除旧 Chroma Chunk，再生成并写入新 Chunk；后续入库失败时，旧向量记录可能已丢失。原始文件的最小恢复保护不等于向量数据库事务回滚。评测过程中应避免更新固定 Corpus，以免资料变化混入版本对比。发现异常应记录实际条件与失败现象，不能把基础设施故障自动解释为检索或 Agent 能力下降。
