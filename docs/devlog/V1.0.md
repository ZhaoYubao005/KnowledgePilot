## 2026-09-14：Agent Loop 主体实现、异常保护与自动化测试

### 一、版本目标

V1.0 的目标是将 V0.9 的单步 Tool Calling 升级为可重复决策的 Agent Loop。

V0.9 的流程在第一次模型请求产生 Tool Call 后，只执行 `tool_calls[0]`，再进行一次不携带 tools 的固定最终请求。V1.0 改为以下循环：

```text
Decision
↓
Action
↓
Observation
↓
再次 Decision
↓
Stop
```

当前 Stop 条件包括：

- 模型不再返回 `tool_calls`，任务以 `completed` 结束。
- 达到最大决策轮数，任务以 `max_steps` 结束。

### 二、主要实现

核心入口：

```python
chat_with_ollama(messages, max_steps=5)
```

当前实现位于：

```text
src/knowledge_pilot/llm/ollama_client.py
```

已经实现的控制流程如下：

1. 使用 `for step in range(max_steps)` 驱动 Agent Loop，默认最多进行 5 轮 LLM Decision。
2. 每轮循环都重新构造 Ollama payload，并同时携带：

   ```text
   calculator_schema
   search_knowledge_base_schema
   ```

3. 如果模型没有返回 `tool_calls`，直接把当前 assistant content 作为最终答案返回，并设置：

   ```text
   stop_reason = completed
   ```

4. 如果模型返回 Tool Call，先把 assistant Tool Call 消息追加到 `messages`。
5. 使用 `for tool_call in tool_calls` 遍历并执行同一轮中的全部 Tool Call，不再只处理第一项。
6. 每个 Tool Call 通过 `execute_tool_call()` 执行，形成 Action。
7. Tool Result 被写回为 `role="tool"` 消息，形成 Observation；下一轮模型仍能看到完整 messages 和全部 tools。
8. Tool 执行异常不会直接中断 Agent，而是转换为：

   ```text
   Tool execution failed: <错误信息>
   ```

   该错误同时进入 Observation 和 Agent Trace，随后 Agent 继续下一轮 Decision。
9. 如果每一轮都继续产生 Tool Call，循环达到 `max_steps` 后返回固定的最大步骤提示，并设置：

   ```text
   stop_reason = max_steps
   ```

#### Agent Trace

每次 Tool 执行都会追加一条 Trace，字段为：

```python
{
    "step": step + 1,
    "tool": safe_tool_name,
    "arguments": arguments,
    "result": result,
}
```

其中 `step` 表示 LLM 决策轮次；同一轮出现多个 Tool Call 时，它们拥有相同的 step 值，但会分别形成 Trace 和 Observation。

#### Agent Result

`chat_with_ollama()` 的两个退出分支都返回统一结构：

```python
{
    "answer": ...,
    "trace": [...],
    "stop_reason": "completed" | "max_steps",
}
```

- `answer`：模型最终回答；达到最大步骤时为固定终止提示。
- `trace`：本次 Agent 执行过的 Tool Action 记录。
- `stop_reason`：当前仅有 `completed` 和 `max_steps`。

#### Malformed Tool Call 处理

当前已对两类畸形 Tool Call 做保护：

1. 缺少 `function.name`：

   - 不调用 Tool Executor。
   - 使用 `safe_tool_name = "unknown_tool"`。
   - 生成 Error Observation：

     ```text
     Tool execution failed: Tool call missing function.name
     ```

   - Trace 中的 `tool` 记录为 `unknown_tool`。

2. 缺少 `function.arguments`：

   - 不调用 Tool Executor。
   - 保留已经提供的 Tool name。
   - Trace 中的 `arguments` 记录为 `None`。
   - 生成 Error Observation：

     ```text
     Tool execution failed: Tool call missing function.arguments
     ```

两类错误都会写回 messages，并允许 Agent 继续下一轮 Decision，不再因后续直接索引缺失字段而抛出 `KeyError`。

### 三、V0.9 → V1.0 架构变化

相对当前封版 HEAD 中的 V0.9 实现，本次变化为：

- 移除了固定的 `final_payload`、`final_response` 和 `final_data` 单次收尾逻辑。
- 移除了只执行 `tool_calls[0]` 的限制。
- 从“第一次 LLM 决策 + 一次固定 Final Answer 请求”改为循环式 LLM Decision。
- 每次 Observation 写回后，下一轮 payload 仍携带全部 tools，模型可以再次选择 Tool。
- 同一轮模型返回多个 `tool_calls` 时，当前轮全部执行。
- 增加 `max_steps` 边界，避免模型持续请求 Tool 而无限循环。
- 返回值从单个字符串升级为统一的 Agent Result 字典。

V1.0 当前实现的是受 `max_steps` 约束的顺序 Agent Loop，没有引入 Planner、并行 Tool Executor 或额外 Agent 框架。

### 七、开发过程中发现的问题与修复

#### 1. Chroma count 硬编码导致集成测试失败

V0.9 封版时正式 Collection 有 30 条数据，旧集成测试硬编码断言：

```python
collection.count() == 30
```

V1.0 测试文档入库后，正式 Collection count 合理增加为 31，导致旧断言失败。该失败不是检索功能退化，而是测试把可增长的数据总量误当成固定业务契约。

当前已删除 `collection.count() == 30` 的脆弱断言，继续验证真正稳定的契约：

- Collection 名称正确。
- `search_knowledge_base()` 返回 list。
- 返回 3 条结果。
- 每条结果字段严格为 `content + source`。
- content 非空且 source 非 `None`。

#### 2. 新数据在旧运行进程中未立即出现

调试过程中观察到：V1.0 测试数据完成入库后，已经启动的旧运行进程没有立即检索到新记录；重启程序后恢复正常。

目前只记录该现象。现阶段没有足够证据确认是客户端缓存、Collection 生命周期、并发访问还是其他原因，因此不对根因作武断结论。

#### 3. 畸形 Tool Call 可能触发 `KeyError`

旧的异常处理路径虽然能捕获 Tool Executor 抛出的异常，但后续仍可能直接访问缺失的 `function.name` 或 `function.arguments`，导致 `KeyError` 逃逸并中断 Agent Loop。

当前修复为：

- 使用安全字段读取。
- 在执行 Tool 前校验 name 与 arguments。
- 缺少 name 时使用 `unknown_tool`。
- 把校验错误统一转成 Error Observation。
- Trace 与 Tool Observation 使用相同的安全工具名和错误结果。
- 错误写回后继续下一轮 LLM Decision。

两个 Malformed Tool Call 自动化测试已经覆盖缺 name 和缺 arguments 两条路径。

### 八、当前非阻塞技术债

以下项目尚未解决，但当前不阻塞 Agent Loop 主流程验证：

- 正式命令行入口中的 `str(agent_result["answer"])` 有轻微冗余。

### 十一、RAG Pipeline 的 Agent Result 兼容修复

V1.0 将 `chat_with_ollama()` 的返回值由单个字符串升级为统一的 Agent Result：

```python

    "answer": ...,
    "trace": [...],
    "stop_reason": ...,
}
```

本次采用保持旧接口的方案 A，在 RAG Pipeline 边界提取 Agent Result 中的最终答案：

- `chat_with_ollama()` 继续返回完整 Agent Result。
- `answer_with_rag()` 继续返回答案字符串与来源列表。
- 本次没有把 `trace` 或 `stop_reason` 扩展进 RAG Pipeline 的返回值。
