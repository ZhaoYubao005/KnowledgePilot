## 3. SQLite 存什么，为什么不用全局列表

`memory/store.py:49` 创建的真实表结构为：

```sql
CREATE TABLE IF NOT EXISTS sessions (
    session_id TEXT PRIMARY KEY,
    revision INTEGER NOT NULL CHECK(revision >= 0),
    turns TEXT NOT NULL
)
```

每个会话占一行，turns 存 JSON 数组；一个数组元素就是完整的 query/answer 对。这里没有单独的 user、assistant、tool 或 system 消息表，也不存工具轨迹或全部模型中间状态。SQLite 文件位于 `KP_DATA_DIR/sessions.sqlite3`，与既有 Chroma 数据根同受 `KP_DATA_DIR` 控制，但两者不是同一个数据库。

`config.py:31` 保留历史的 CWD 相对默认 `data`。若显式设置 `KP_DATA_DIR`，必须是绝对路径。因此从不同目录启动时先核对数据根，不要把打开了另一个空库误判为“持久化丢失”。`SessionStore.__init__` 会将传入路径 resolve 成绝对路径，避免对象创建后切换 CWD 改变它的目标。

全局 list 会在进程重启后消失，也容易把不同会话混在一起；单个 JSON 文件在并发覆盖时还需要自行处理事务。这里用标准库 SQLite 持久化，并依赖事务与 revision 防止旧结果覆盖新结果，没有新增服务或数据库依赖。

### 标识、错误和损坏数据

`store.py:94` 使用 `secrets.token_urlsafe(32)` 生成 256 位随机材料形成的 43 字符 URL 安全 ID。`store.py:70` 在执行 SQL 前用完整正则 `[A-Za-z0-9_-]{43}` 校验；非法和不存在的 ID 都抛 `SessionNotFound()`。所有涉及 ID 的 SQL 使用 `?` 参数绑定，字符串不会拼进 SQL。

`SessionConflict` 固定消息为 `Session changed. Please retry.`；`SessionDataError` 固定消息为 `Session data unavailable.`，均不包含 SQL、数据库路径或用户内容。`store.py:80` 校验 revision、解析 JSON；根对象不是 list 或 JSON 已损坏时安全失败。根对象是 list 但部分记录无效时，`context._valid_turn` 将无效轮次筛掉。`clear` 不必解析旧 turns，因此可以清空内容损坏但 revision 仍合法的会话。

### 连接和锁的生命周期

`store.py:56` 的 `_connection()` 每次操作创建连接，设置 `busy_timeout=2000` 毫秒，退出时关闭连接。sqlite3 上下文负责提交或回滚，外层 finally 负责 close；`with connection` 本身不等于关闭连接。append 和 clear 在短事务内执行 `BEGIN IMMEDIATE`，等待锁有界；没有跨模型请求持有的连接或事务。

会话预算控制“每个会话的保留历史”，不控制数据库总量。没有会话数量上限、TTL 或后台清理；创建很多 session 仍会增长数据库。DELETE 只把 turns 写成空数组并推进 revision，不删除会话标识，也不保证 SQLite 旧页、备份或文件系统上的内容被物理安全擦除。

## 4. 应用层两阶段：先推理，再比较版本提交

真实边界在 `memory/service.py:14`。这里的“两阶段”指推理与提交两个应用步骤，不是分布式事务协议，也不是让 SQLite 在模型运行期间保持一个大事务。

1. **快照与推理阶段**：读取 `{revision, turns}`；将有界历史转为消息；调用 execute 执行 Agent 或 Workflow。store.read 返回前连接已经关闭，模型超时不会占着会话数据库写锁。
2. **提交阶段**：仅当 Workflow `status == 'completed'` 或 Agent `stop_reason == 'completed'` 时，验证 answer 是非空字符串，再调用 `append(..., expected_revision=snapshot['revision'])`。append 开启短写事务，重新读取当前 revision，比较成功才裁剪并写回 turns，同时 revision 加一。

这就是 CAS（compare and swap）在这里的含义。比较和更新被同一个 `BEGIN IMMEDIATE` 事务包住，不是先在事务外比较、再无条件写入。

两个并发请求若都读到 revision=3，可以同时完成模型推理；第一个提交写成 revision=4，第二个提交发现 4≠3，抛 SessionConflict。HTTP 层返回 409，不用第二个结果覆盖第一个，也不自动重新请求模型。调用方需要重新读取当前历史后自行决定是否重试。

clear 同样在事务中读取 revision 并加一。假设推理中的请求读到 revision=4，用户随后 clear 写成 revision=5；旧请求再来提交时 CAS 失败，不能把清空前的内容重新带回来。

失败的路由、no_results、模型异常、达到 max_steps 都不进入成功历史。`service.py:22` 还单独拦截“声称 completed 但 answer 为空白”的 Agent 返回，转成 `ModelResponseError('llm')`，避免把空答案存进历史。注意这里只判断最终状态；原 Agent 若曾在中间产生工具失败观察结果、后来仍给出 completed 答案，最终问答仍可能被保存，不能称为每个中间工具都成功。

## 5. 上下文按完整问答对裁剪

`memory/context.py:10` 只接受恰好具有 query、answer 两个键且值均为非空白字符串的 dict。调用者提供的 `{'role': 'system', ...}` 或附带 role 的伪装记录会被拒绝。`history_messages` 只自行生成 user/assistant 两种角色，不恢复历史 system 或 tool 角色。

`select_turns` 从最新记录向前扫描：

1. 丢弃类型不对、键不对、空白或非字符串记录。
2. 以 `len(query) + len(answer)` 计入历史字符预算。
3. 一整个问答对放不下就跳过，不截半句、不只留下 assistant 答案；更旧但能放下的对话仍有机会保留。
4. 达到 max_turns 后停止，最后 reverse 恢复时间顺序，并返回新 list 和新 dict。

所以“最近”是按预算挑选最近可容纳的完整有效轮次，结果未必是连续的一段后缀。超大的最新问答可能整体不保留，但不会强迫所有更小的旧记录一同消失。append 对数据库原始历史加上新 pair 后统一裁剪一次；不要先按新预算把旧历史裁剪一遍再加新轮次，否则更旧、较小、原本能放下的 pair 可能被过早丢失。

默认最多 10 对、12000 字符。这是 Python 字符长度，不是精确 token、UTF-8 字节数或完整请求预算。system 提示词、当前 query、工具证据和执行上下文不包含在这个历史预算里；因此这不是整个模型上下文窗口的上限。当前 query 始终在历史后单独加入，不能因为历史裁剪把当前问题一起丢掉。已成功回答但超过存储预算的 pair 可能不进入保留 turns，而 revision 仍然增加。

环境配置由 `memory/service.py:8` 和 `runtime_settings.py` 读取：

- `KP_SESSION_MAX_TURNS`：默认 10，应用范围 1..100。
- `KP_SESSION_MAX_CHARS`：默认 12000，应用范围 256..100000。
- `KP_TOOL_MAX_ATTEMPTS`：默认 2，范围 1..3，表示总尝试次数，包含第一次，不是“额外重试两次”。

底层 context/store 允许零预算，便于独立使用和测试；生产环境变量的边界更严格。非法配置抛已有 ConfigurationError，不悄悄变成默认值。原 config 模块未增加这些字段；runtime_settings 保持新版本设置独立，get_session_store 每次调用传入自己的限制，没有全局可变历史。

## 7. Recovery：分类、重试谓词与安全事件

`tools/recovery.py:32` 先分类异常，`recovery.py:78` 再决定能否重试。**异常类别不等于重试资格**：即使 category=model_timeout，如果是 `ModelTimeout('llm')`，这里也不重试。

类别包括：`model_timeout`、`model_unavailable`、`model_response_error`、`model_error`、`network_timeout`、`network_unavailable`、`invalid_arguments`、`tool_failed`。其中 TypeError/ValueError 属于 invalid_arguments；未知异常属于 tool_failed。

重试需要同时满足：

```python
name == 'search_knowledge_base' and (
    isinstance(error, (ModelTimeout, ModelUnavailable)) and error.operation == 'embedding'
    or isinstance(error, (requests.Timeout, requests.ConnectionError))
)
```

真实源码将这几个条件拆成 transient_model、transient_network 和 retryable。只读检索的临时 Embedding/网络故障可重试；calculator 除零、参数错误、LLM 故障、非法模型响应、未知工具或其他工具均不自动重试。未来接入写操作时不能仅把名字加进白名单，必须先讨论幂等性。这个 helper 本身不是工具授权或参数 Schema 校验器，仍由原 Schema/Registry 负责允许哪些工具。

`execute_with_recovery` 是普通有界 for 循环，没有睡眠、退避、图后向边或持久化重试队列。max_attempts 必须是 1..3 的真正 int，拒绝 bool。连续可重试失败达到上限时，`RecoveryResult.error == 'exhausted'`；最后一个 event 仍保留真实异常分类。

每次尝试产生一个安全事件，例如：

```json
{"stage":"retrieve","attempt":1,"status":"failed","category":"model_timeout","retryable":true}
```

字段只有 stage、attempt、status、category、retryable。stage 是 retrieve 或 tool；成功时 category=null、retryable=false。最终失败事件的 retryable=true 仅说明“属于可重试故障”，不表示还会有下一次。events 不含 query、参数、证据或异常文本。

`RecoveryResult.exception` 只供内部保留原异常类型，不参与 repr，也不能被直接序列化对外返回。Workflow 对 ModelError 重新抛出原异常并附加安全 diagnostics，继续已有 502/503/504 HTTP 映射；普通工具异常维持领域 `failed`，由调用者检查 status。返回证据或数值不合法时，graph 将原本 succeeded 的事件改为 failed/invalid_result；这属于执行后验证，不触发重试。

## 8. 原图与 trace：重试次数不等于节点次数

V1.5 的图仍是同一张无环图：

```text
START -> initialize -> decide
                        | direct -> generate -> finish -> END
                        | rag    -> retrieve -> generate 或 finish
                        | tool   -> tool     -> generate 或 finish
                        | invalid_route      -> finish
```

节点定义位置为 `graph.py:53 initialize`、`:59 decide`、`:73 retrieve`、`:101 tool`、`:124 generate`、`:141 finish`；条件函数是 `:144 after_decide` 和 `:149 after_execution`。State 新增 diagnostics，不将 session 历史塞进公开 State/响应；history 通过单次图构造时的局部闭包传入。

重试发生在 retrieve/tool 节点内部，旧 trace 顺序不变：

- direct：`initialize, decide, generate, finish`。
- RAG 成功，包括第一次失败、第二次恢复：`initialize, decide, retrieve, generate, finish`。
- calculator 成功：`initialize, decide, tool, generate, finish`。
- invalid_route：`initialize, decide, finish`。
- 空检索或普通检索失败：`initialize, decide, retrieve, finish`。
- 普通工具失败：`initialize, decide, tool, finish`。

ModelError 从图中抛出时，不伪造一个完成 trace；HTTP 错误携带固定 detail，必要时附带 diagnostics。正常一次工具成功的响应不新增 diagnostics 键；有多次尝试或失败才附加，见 `_invoke_workflow:185`。这样保留 V1.5 正常成功响应形状，不能把省略 diagnostics 误读为“没有执行工具”。

最多五个业务节点的边界继续成立；一次检索节点现在可能执行最多三次检索，所以 V1.5 的“一次工具执行”描述不再适用于开启恢复的检索。`recursion_limit=8` 是图遍历防线，不是工具重试上限。

## 10. Python、dict/list 和 sqlite3 容易踩的坑

1. `bool` 是 int 的子类。配置和尝试次数需要 `type(value) is int`，否则 True 会被当成一次尝试；计算器结果也专门拒绝 bool，不能将 true 当成数值 1。
2. `TypedDict` 只是类型说明，Pydantic 才在边界实际验证。`dict.get()` 只是取值，不证明 answer 类型和非空，提交前仍需校验。
3. list/dict 可变。不要给函数默认参数写 `history=[]`，不要让会话共用列表，也不要对已返回的历史直接原地 append。context 为结果复制记录，graph 用 `state['trace'] + ['node']` 返回新列表。
4. 浅拷贝只复制一层。当前历史记录只有两个字符串，所以新 dict 足够；若未来加入嵌套 metadata，不能假定 `dict(record)` 已经隔离所有嵌套对象。旧 Agent 会修改 messages，session service 必须为每次调用重新构造列表。
5. “SELECT 后 UPDATE”本身不能防并发覆盖。只有把重新读取、revision 比较与写入放进同一事务，才能保护这个 CAS；数据库文件存在不代表应用的并发语义正确。
6. `with sqlite3.connect(...)` 负责提交/回滚，不保证 close。也不要把同一连接跨线程共享；这里每次操作新建连接，使线程各自拥有连接。
7. SQL 参数用 `?` 绑定，不能用 f-string 拼 ID。错误处理也不能把完整 sqlite 异常字符串发给客户端。
8. 一个轮次数为 1 的历史包含两个模型消息。`len(turns)`、`len(messages)`、字符预算、revision 是四个不同量，clear 后 revision 可以大于零而 turns 为空。
9. SQLite 持久化只说明保存了记录；模型能否回答还取决于事实是否仍在保留历史、是否被送进模型、模型是否遵守提示。只检查 HTTP 200 或 answer 非空不能证明记忆有效。
10. RecoveryResult 使用 `field(default_factory=list)`，避免 dataclass 实例共享事件列表。异常对象留在内部字段，不应使用通用 `asdict` 把整个 RecoveryResult 返回给客户端。
